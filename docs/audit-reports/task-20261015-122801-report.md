2. CORRECTION 1 — HISTORY IDENTIFICATION & subject_id LIFECYCLE
2.1 Schema Definition & Uniqueness Scope
To prevent history loss upon canonical row deletion (GAP 1), every per-entity version table introduces a mandatory subject_id column.

Uniqueness Scope Selection: Option U1 (Globally Unique Across All Entity Types).
Format: String representation of a UUIDv4 (e.g., subj_018f2b3c-4d5e-7890-a1b2-c3d4e5f6a7b8).
Justification: Option U1 prevents cross-entity identifier collision, simplifies global correlation across events/traces, eliminates composite key requirements in generic replay/event logs, and ensures uniform lookup semantics across all 5 versioned entities.
subject_id Rules:
subject_id is immutable for the lifetime of the logical entity. Updating canonical row fields never modifies subject_id.
All version rows for a given logical entity share the exact same subject_id.
Canonical primary key (entity_id) and subject_id are separate identifiers. entity_id is the local database primary key; subject_id is the stable logical entity identity.
2.2 Representative Version Table Schema Sketch (e.g. prediction_versions)
CREATE TABLE prediction_versions (
    version_id VARCHAR(36) PRIMARY KEY, -- Immutable version UUID
    subject_id VARCHAR(64) NOT NULL,    -- Option U1 stable logical entity ID (INDEXED)
    entity_id INTEGER NULL REFERENCES predictions(id) ON DELETE SET NULL, -- FK to canonical row
    version_number INTEGER NOT NULL,    -- Sequential integer per logical entity (1, 2, 3...)
    valid_time TIMESTAMP WITH TIME ZONE NOT NULL,    -- Domain effective time
    recorded_time TIMESTAMP WITH TIME ZONE NOT NULL, -- System recording time
    idempotency_key VARCHAR(128) NULL,               -- Unique key per subject_id
    content_hash VARCHAR(64) NOT NULL,               -- SHA-256 canonical payload hash
    content JSON NOT NULL,                           -- Immutable snapshot of canonical domain fields
    created_by VARCHAR(128) NULL,                    -- Actor/source
    CONSTRAINT uq_pred_ver_subject_num UNIQUE (subject_id, version_number),
    CONSTRAINT uq_pred_ver_subject_idem UNIQUE (subject_id, idempotency_key)
);
CREATE INDEX idx_pred_ver_lookup ON prediction_versions (subject_id, recorded_time, valid_time);
2.3 FK Behavior & Deletion Dynamics
FK Constraint: entity_id references the canonical table (e.g. predictions(id)) with ON DELETE SET NULL.
Independent PK: Each version row possesses an independent primary key (version_id).
No Cascade Deletion: Zero CASCADE DELETE constraints exist on version tables. Deleting a canonical row sets entity_id = NULL on historical version rows but leaves all version records intact.
Independent Reading: Queries for history execute directly against prediction_versions WHERE subject_id = :subject_id without joining the canonical predictions table.
2.4 Logical Entity Assignment & Restoration Rules
New Entities (Post-Rollout):
Assigned a fresh UUIDv4 subject_id at creation time in Service.create().
Stored on the canonical row and attached to Version 1.
Pre-Versioning Existing Entities:
Backfilled during M-02 migration with a deterministic UUID derived from (entity_type, canonical_id) (e.g., UUIDv5(NAMESPACE_URL, "cosmos:prediction:123")).
Restoration vs. New Entity Distinction:
Restoration of Same Logical Entity: Canonical row is re-inserted or undeleted while preserving the original subject_id. Version numbering continues sequentially ($N+1$). A RESTORED domain event is recorded.
Creation of New Entity with Similar Data: A fresh subject_id is assigned. Prior history under the previous subject_id is NOT linked, even if all domain payload fields match identically.
Restoration Mechanism Status:
The repository currently has NO canonical undelete/restore API mechanism (UNRESOLVED_RESTORATION_GAP). Restoration rules are defined for contract completeness, but actual restoration workflows are classified as a dependency for M-03/M-04.
2.5 Updated Invariant I6 Enforcement Statement
Invariant I6: Deleting or corrupting the canonical row must not destroy or corrupt version history.
Enforcement: Version rows carry an independent primary key (version_id), a stable indexed logical identifier (subject_id), and an ON DELETE SET NULL foreign key (entity_id). Deleting a canonical row leaves all version rows retrievable by subject_id.
Status: REQUIRES_M-02_CHANGE (Table schemas must be created in M-02).
3. CORRECTION 2 — QUERY A & QUERY B SEMANTICS, TIE-BREAKING, & AMBIGUITY
3.1 Unambiguous Query Definitions
To resolve GAP 2, the contract explicitly defines and distinguishes two temporal selection functions:

Query A — Domain-Time Reconstruction under a Knowledge Cutoff (knowledge_about_domain_time): Answers: "What did the system know at system time $T_{\text{know}}$ about the state valid at domain time $T_{\text{valid}}$?"

Filter candidates where recorded_time <= T_know.
Filter remaining candidates where valid_time <= T_valid.
Sort remaining candidates by valid_time DESC, recorded_time DESC, version_number DESC.
Select Top 1 candidate.
If candidate set is empty, return UNAVAILABLE_HISTORICAL_STATE.
Query B — Knowledge-Latest Reconstruction (knowledge_latest): Answers: "What was the latest known state recorded by the system at or before system time $T_{\text{know}}$, regardless of domain effective time?" Contract Option Selected: Option B1 (Strict Knowledge-Latest).

Filter candidates where recorded_time <= T_know.
Sort remaining candidates by recorded_time DESC, version_number DESC.
Select Top 1 candidate.
If candidate set is empty, return UNAVAILABLE_HISTORICAL_STATE.
3.2 Tie-Breaking, Ordering, & Isolation Rules
Deterministic Order: version_number is a strictly monotonic, unique sequential integer per subject_id.
Tie-Break Rule: When multiple candidate versions share the exact same valid_time and recorded_time, the version with the highest version_number is selected.
Future Isolation Guarantee: A version recorded after $T_{\text{know}}$ (recorded_time > T_know) is STRICTLY EXCLUDED from candidate evaluation for queries at cutoff $T_{\text{know}}$, even if its version_number is higher, its valid_time is earlier (backdated correction), or its payload is more complete.
3.3 Ambiguity & Corruption Error Contract
If the historical record contains damaged, unparseable, duplicate version_number entries, or hash mismatches among eligible candidates:

Behavior: The query MUST NOT return an arbitrary version and MUST NOT silently fall back to canonical live rows.
Error Return: Returns an explicit structured result:
{
  "status": "ERROR",
  "error_code": "AMBIGUOUS_OR_CORRUPTED_HISTORY",
  "message": "Historical version payload hash mismatch or duplicate sequence detected for subject_id",
  "subject_id": "subj_018f2b3c-4d5e-7890-a1b2-c3d4e5f6a7b8",
  "as_of_knowledge": "2026-10-15T10:00:00Z"
}
Distinction: AMBIGUOUS_OR_CORRUPTED_HISTORY indicates data integrity failure, whereas UNAVAILABLE_HISTORICAL_STATE indicates valid query context prior to the first recorded version.

4. CORRECTION 3 — IDEMPOTENCY & VERSION ALLOCATION
4.1 Required Design
To close GAP 3, idempotency and concurrent version allocation semantics are specified as follows:

Storage: idempotency_key (nullable string) stored directly on each version row.
Uniqueness Scope: (subject_id, idempotency_key).
Duplicate Request Behavior:
If a write request is received with an idempotency_key that already exists for the given subject_id, the write operation is skipped (no-op) and the existing version row is returned.
Concurrent Version Allocation Mechanics:
Database unique constraint UNIQUE (subject_id, version_number).
Write operations execute SELECT MAX(version_number) FROM versions WHERE subject_id = :subject_id WITH UPDATE (pessimistic lock) or attempt insertion at $N+1$.
If a concurrent write causes a unique constraint violation on (subject_id, version_number), the service catches the exception and retries allocation up to 3 times with exponential backoff.
Reader Visibility Rules:
Canonical row update, version row insertion, and optional DomainEvent recording execute in a single SQLAlchemy db.commit() transaction boundary. Readers never observe uncommitted or partial updates.
