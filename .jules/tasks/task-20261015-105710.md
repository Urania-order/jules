0. NORTH STAR
============================================================

M-01 concluded READY_FOR_M-02 with a proposed atomic task plan.
However, the M-01 gap analysis itself documented that:

- Prediction, Hypothesis, DiscoveryRecovery, Phenomenon, and
  PotentialPhenomenon lack point-in-time content versioning.
- A bare version_id counter does NOT preserve prior content.
- In-place updates to these entities overwrite historical state.
- The system can READ past EvaluationRecord entries but cannot
  reconstruct the historical content of the evaluated target
  because entity content is not versioned.

Therefore, before implementing M-02 (Content Versioning Model
Extensions), the versioning CONTRACT must be explicitly defined.

Mission:
Define the versioning contract that will:

1. Preserve immutable snapshots of prior entity content.
2. Enable point-in-time reconstruction of entity content at a
   given as_of timestamp.
3. Coexist with existing single-row CRUD operations.
4. Preserve existing append-only invariants (Observation,
   ExperimentRun.status_history, EvaluationRecord).
5. Integrate cleanly with DomainEvent (ADR-0009) without
   duplicating event recording.
6. Avoid creating a second versioning or event system.

This task is AUDIT + DESIGN ONLY.

Do NOT modify code.
Do NOT modify models.
Do NOT modify schemas.
Do NOT modify database.
Do NOT create migrations.
Do NOT modify tests.
Do NOT create a commit.

The deliverable is a written contract proposal with justification.

NOTE 11 — Bitemporal correctness (MANDATORY)
The contract must distinguish, where required:
- valid_time: when a version is considered valid in the domain.
- recorded_time: when the system persisted or learned about that
  version.
- as_of: the temporal cutoff requested by the caller.

Do not assume that one timestamp can answer both of these
questions:
1. What did the system consider valid at domain time T?
2. What information had the system actually recorded by system
   time T?

The report must explicitly state whether the chosen contract
supports:
A. Current historical reconstruction using the latest known
   version for a domain-time cutoff.
B. Historical knowledge reconstruction using only information
   recorded by a system-time cutoff.
C. Both forms of reconstruction.

If the contract supports only A, it must not claim B.

For corrections recorded after the original effective time,
specify whether previous reconstruction results remain
reproducible and how the correction is represented.

If the repository cannot support the required temporal semantics
within the approved scope, identify the limitation and make it a
decision-gate issue.

NOTE 12 — Atomic version creation (MANDATORY)
The contract must define a consistency boundary for each entity
update.
The canonical entity update and immutable version creation must
either both become durable or neither become durable, unless the
audit proves that this guarantee cannot be provided by the
existing persistence architecture.
If DomainEvent recording is required for the operation, specify
whether it participates in the same transaction.
If atomicity across these writes is unavailable, do not claim
atomic consistency. Document the exact limitation and propose the
smallest safe alternative, including how incomplete writes are
detected and repaired.

The contract must also define:
- How concurrent updates are serialized or rejected.
- How duplicate retries are detected.
- How revision numbers are allocated safely.
- How readers avoid observing a partially completed update.
- Whether the current canonical row can be rebuilt or checked
  against the latest committed version.

Do not prescribe a transaction implementation without first
inspecting the actual database and session-management patterns.

NOTE 13 — Reconstruction levels (MANDATORY)
The report must distinguish these levels and state which are
supported:
1. Entity reconstruction: recovering one entity's persisted
   content at a specified cutoff.
2. Relationship reconstruction: recovering the historically
   correct links between entities.
3. Evidence reconstruction: recovering the observations and
   evidence available to a particular analysis.
4. Knowledge reconstruction: recovering what the system had
   recorded or could legitimately use at a specified time.
5. Evaluation replay: rerunning an evaluation using historically
   correct inputs, criteria, configuration, and relevant
   execution semantics.
6. Reproducibility verification: comparing a recomputed result
   with the originally persisted evaluation result.

Do not claim a higher level is supported merely because a lower
level works.
For every unsupported level, identify the missing versioned data,
dependency, or contract. State which future task must address it.
A content snapshot is not proof that related entities, evidence,
criteria, or execution configuration are historically
reconstructable.

NOTE 14 — Historical coverage and confidence (MANDATORY)
Every reconstructed result must make it possible to distinguish:
- A historically verified snapshot.
- A snapshot captured only when versioning was introduced.
- A reconstruction derived from incomplete historical evidence.
- An unavailable historical state.

A backfilled snapshot must not be represented as proof of content
at an earlier timestamp unless independent evidence establishes
that content.

The contract must specify how incomplete historical coverage is
represented to callers and how temporal queries behave when their
cutoff precedes the first verified version.

No fallback to the current canonical row is allowed when the
requested historical state is unavailable.

The report must include at least one worked conceptual example
showing:
- An entity created before versioning exists.
- The first snapshot captured at rollout.
- A query for a date before rollout.
- The correct result and its explanation.

NOTE 15 — Scope containment

M-02A must not silently expand into a full architectural

NOTE 16 — Corrections with backdated valid_time (MANDATORY)

The contract must define exactly how a version is selected when a
correction is recorded at system time T_record but is declared to
be effective from domain time T_valid, where T_valid < T_record.

The report must distinguish and answer separately:

- Question A: "What did the system consider valid at domain time T?"
- Question B: "What did the system know at system time T?"

For a correction with T_valid < T_record:
- If the contract supports only Question A, say so explicitly and
  do not claim historical knowledge reconstruction.
- If the contract supports only Question B, say so explicitly and
  do not claim domain-valid reconstruction.
- If both, define how each query type selects its version and how
  the two results differ.

The report must include at least one worked conceptual example.
State which query type the contract supports and which it does not.

Declaration of valid_time and recorded_time is not sufficient. The
contract must show the two are actually used differently by
version selection.

NOTE 16.1 — Worked example must state all assumptions

The worked conceptual example required by NOTE 16 must:

1. Explicitly list every version present in the example, including
   version identifier, valid_time, recorded_time, and content value.

2. Show the full version-selection process for BOTH queries:
   - Query A (domain-time cutoff): list all versions with
     valid_time <= T, sorted, and select the latest.
   - Query B (knowledge-time cutoff): list all versions with
     recorded_time <= T, sorted, and select the latest.

3. Not assume that the "original value" is always the answer for
   Query A. The answer must be derived from the version set.

4. Show at least one example where a later correction changes
   Query B but not Query A, and at least one example where a
   correction changes both.

5. If the contract cannot distinguish the two queries in a given
   case, state that explicitly rather than defaulting to one
   interpretation.

NOTE 16.2 — Two-dimensional temporal selection (MANDATORY)

For a full bitemporal model, Query A is NOT simply "the version
valid at domain time T". It must be:

    Query A (domain-time cutoff):
    1. First restrict to versions whose recorded_time <= T_know,
       where T_know is the knowledge-time cutoff implied by the
       caller's request context.
    2. Then, among those, select the version whose valid_time is
       the latest <= T_valid.

    Query B (knowledge-time cutoff):
    1. Restrict to versions whose recorded_time <= T_know.
    2. Select the latest.

That is, a full bitemporal model requires BOTH restrictions
simultaneously for Query A:
- recorded_time <= knowledge cutoff
- valid_time <= domain cutoff

If the contract only applies valid_time <= T for Query A, it
supports a single-axis temporal model, NOT a full bitemporal
model. The report must state this explicitly.

The report must show, in the worked example:
- The knowledge-time cutoff used for each query.
- Which versions survive each restriction.
- The exact version selected by each query.
- Whether the two queries produce the same or different results.

If the repository cannot support both restrictions within the
approved scope, classify the limitation as a decision-gate issue
and do not claim full bitemporal reconstruction.

NOTE 17 — Required invariants (MANDATORY)

The contract must enumerate invariants that versioned entities must
satisfy, and state for each whether it can be guaranteed by the
existing persistence architecture or requires an M-02 implementation
change.

Required invariants:

I1. Every successful mutation of a versioned entity produces exactly
    one corresponding immutable version row, unless the mutation is
    a no-op explicitly recorded as such.

I2. Version numbers are unique per entity.

I3. A repeated request with the same idempotency key does not create
    a duplicate version. If idempotency is not supported, say so.

I4. Each version stores a content hash that matches the canonical
    serialization of the stored content. Mismatch must be detectable.

I5. A reader must never observe a partially completed update. If
    canonical row, version row, or event can diverge under failure,
    state the exact divergence and the detection/repair procedure.

I6. Deleting or corrupting the canonical row must not destroy the
    version history. History must remain independently readable.

    I6 enforcement requirements (MANDATORY):
    A separate version table alone does NOT guarantee I6.
    The report must state:
    - The exact FK delete behavior proposed (CASCADE, SET NULL,
      RESTRICT, or no FK).
    - Whether version rows have an independent primary key that
      survives canonical-row deletion.
    - Whether version rows can be read without joining the
      canonical entity.
    - Whether the version table has any cascade rule that would
      delete rows when the canonical row is deleted.
    - If I6 cannot be guaranteed by the proposed schema, classify
      it as REQUIRES_M-02_CHANGE or NOT_GUARANTEED.

I7. The current canonical row must be either the latest committed
    version or provably consistent with it. Divergence must be
    detectable.

I8. Version selection for a given as_of cutoff must be deterministic
    when multiple versions share a timestamp. Specify the tie-break.

For each invariant state one of:
- GUARANTEED_BY_EXISTING_ARCHITECTURE
- REQUIRES_M-02_CHANGE
- NOT_GUARANTEED (with exact limitation)

Invariants without an enforcement statement are not acceptable.

NOTE 17.1 — Schema contract vs runtime guarantees (MANDATORY)

The contract defines WHAT must be guaranteed.
The existing database and session architecture determines WHETHER
the guarantee can be met without change.

Do NOT classify I1, I5, or I7 as
GUARANTEED_BY_EXISTING_ARCHITECTURE merely because SQLAlchemy is
used.

The report must explicitly inspect and document:
- The actual transaction mechanism in use.
- The isolation level configured for the session/engine.
- SQLAlchemy session lifecycle and commit/rollback behavior.
- Whether concurrent updates are serialized, rejected, or
  unconstrained.
- Whether the current architecture can guarantee atomicity across:
    (a) canonical row update,
    (b) version row insert,
    (c) optional DomainEvent insert.
- Whether any partial-write detection or repair mechanism exists.

Only after documenting the actual runtime behavior may each
invariant be classified.
If runtime guarantees cannot be established within M-02A's
audit scope, classify the invariant as REQUIRES_M-02_CHANGE or
NOT_GUARANTEED, and state the exact missing mechanism.

NOTE 17.2 — Definition of "version" content (MANDATORY)

The contract must define exactly what a version snapshot contains.

Required decisions:

1. Which fields are part of the canonical versioned content.
   - Identify the domain fields that define the entity's meaning.
   - Exclude mutable technical fields (e.g. updated_at) from the
     content hash unless their inclusion is justified and
     documented.
   - State explicitly whether primary key, foreign keys, and
     status fields are included.

2. Whether relationships between entities are part of the
   snapshot.
   - If relationships are NOT snapshotted, state this explicitly
     and classify the corresponding reconstruction level
     (per NOTE 13) as unsupported.
   - Do NOT claim relationship reconstruction if only entity
     content is versioned.

3. How the content hash is computed.
   - Canonical serialization rules.
   - Which fields are included or excluded.
   - How the hash is stored (version row, canonical row, or both).

4. Whether the snapshot is content-only or content-plus-metadata.
   - If metadata (e.g. actor, source, reason) is stored, state
     whether it participates in the hash.

The report must include a concrete field list per versioned entity,
marking each field as:
- INCLUDED_IN_CONTENT_HASH
- STORED_BUT_NOT_IN_HASH
- NOT_STORED

NOTE 18 — Contract readiness vs implementation readiness (MANDATORY)

READY_FOR_M-02_IMPLEMENTATION means the versioning CONTRACT is
specific enough to guide an M-02 implementation.

It does NOT mean any of the following:
- that historical content before versioning rollout is reconstructable,
- that all six reconstruction levels (NOTE 13) are supported,
- that atomicity is already guaranteed,
- that migration of existing rows is already solved,
- that full Temporal Replay is achievable,
- that recomputation verification is possible.

The report MUST explicitly list:
- which reconstruction levels remain unsupported,
- which invariants require M-02 changes,
- which gaps are deferred to M-03 or later.

A decision of READY_FOR_M-02_IMPLEMENTATION is acceptable only if:
- every required invariant (NOTE 17) has an enforcement statement,
- every reconstruction level (NOTE 13) has a supported/unsupported
  classification,
- the temporal semantics (NOTE 16, 16.1, 16.2) explicitly state
  which query types the contract supports,
- NOTE 17.1 runtime audit is complete,
- NOTE 17.2 field list per entity is complete.

If any of these is missing, the correct decision is
NEED_MORE_ANALYSIS.
