1. CORRECTION 1 — HISTORY IDENTIFICATION
============================================================

M-02A GAP:
entity_id with ondelete="SET NULL" leaves version rows without
a lookup key once the canonical row is deleted.

1.1 Introduce subject_id

The corrected schema must include a subject_id column on each
version table. subject_id is the stable identity of the logical
entity, independent of the canonical row.

The report must state:

1. subject_id is immutable for the lifetime of the logical
   entity. Updating the canonical row does not change it.

2. Uniqueness scope must be explicitly chosen:
   - Option U1: globally unique across all entity types.
   - Option U2: unique within an entity type
     (entity_type + subject_id).
   Select exactly one option and justify it.

3. All versions of the same logical entity share the same
   subject_id. A version row carrying a different subject_id for
   the same logical entity is invalid.

4. After canonical row deletion, history remains retrievable by:
   - (entity_type, subject_id), or
   - globally unique subject_id,
   depending on the chosen uniqueness scope.

5. Assignment order must be defined for:
   - new entities created after rollout,
   - existing entities that predate versioning,
   - restored or recreated entities (see 1.3).
   Specify at what moment subject_id is assigned and by what
   mechanism.

6. subject_id must not become a second, inconsistent identifier
   competing with the canonical primary key. The relationship
   between the two must be explicit.

1.2 FK behavior

State explicitly:
- Which FK, if any, links version rows to canonical rows.
- Whether version rows have an independent primary key.
- Whether entity_id may become NULL.
- Whether any cascade rule deletes version rows.
- Whether version rows can be read without joining the
  canonical row.

1.3 Restoration vs new entity

The report must distinguish:

1. Restoration of the same logical entity:
   - original subject_id preserved,
   - version history continues under the same subject_id,
   - restoration is recorded as an event but does not change
     identity.

2. Creation of a new entity with similar data:
   - a NEW subject_id is assigned,
   - prior history under a different subject_id is not reused,
   - even if all field values are identical, the new entity is
     not the same logical entity.

3. If the repository has no defined restoration mechanism:
   - record this as an unresolved case,
   - do not invent restoration behavior,
   - classify the missing mechanism as a dependency for M-02 or
     later.

1.4 Updated I6

Re-state I6 with subject_id as the retrieval key.
Add:
- "Versions remain retrievable by subject_id after canonical
  row deletion."
- "No cascade rule deletes version rows."

Deliverable:
- updated schema sketch for one representative version table,
- explicit FK behavior,
- explicit lookup algorithm by subject_id,
- explicit uniqueness scope decision,
- assignment rules for new, pre-versioning, and restored
  entities,
- updated I6 enforcement statement.

2. CORRECTION 2 — QUERY B SEMANTICS
============================================================

M-02A GAP:
Query B restricts only by recorded_time. It does not answer
"what did the system know at T_know about the state valid at
T_valid".

2.1 Define both queries unambiguously

Query A — domain-time reconstruction under a knowledge cutoff:
  1. Restrict recorded_time <= T_know.
  2. Restrict valid_time <= T_valid.
  3. Order by valid_time DESC, version_number DESC.
  4. Select top 1.

Query B — must be explicitly chosen from:

  Option B1 — strict knowledge:
    1. Restrict recorded_time <= T_know.
    2. Order by recorded_time DESC, version_number DESC.
    3. Select top 1.

  Option B2 — knowledge about a domain date:
    1. Restrict recorded_time <= T_know.
    2. Restrict valid_time <= T_valid.
    3. Order by recorded_time DESC, version_number DESC.
    4. Select top 1.

The report must:
- state which definition of Query B the contract uses,
- if both are needed, define two distinct query names
  (knowledge_latest and knowledge_about_domain_time),
- never conflate them.

2.2 Tie-breaking and ambiguity

When multiple versions share the same valid_time, the contract
must state:

1. The selected version is the latest already recorded by
   T_know, ordered by version_number.

2. A version recorded AFTER T_know must NOT be used for
   reconstruction at T_know, even if it has:
   - a higher version_number,
   - the same valid_time as an earlier version,
   - more complete content.
   Selection is performed only among candidates that passed BOTH
   temporal filters.

3. version_number must be defined as the deterministic order of
   version recording for a specific logical entity, unique within
   that entity.

4. If the contract cannot determine a unique correct version
   because version data is damaged, missing, or internally
   inconsistent, reconstruction must return an explicit error
   result. It must NOT return an arbitrary version and must NOT
   silently fall back.

5. The error result must be distinguishable from:
   - UNAVAILABLE_HISTORICAL_STATE (no version exists before cutoff),
   - a valid reconstruction.

2.3 Worked example

Provide a worked example with at least THREE versions:

- version 1: original,
- version 2: intermediate (valid_time between original and
  backdated correction),
- version 3: backdated correction (valid_time earlier than
  version 2, recorded_time later than version 2).

Show, for each query:
- the full candidate set at each restriction step,
- the selected version,
- at least one case where Query A and Query B differ,
- at least one case where they agree,
- at least one case where reconstruction returns an explicit
  ambiguity error instead of a version.

Deliverable:
- final query definitions,
- tie-break rule,
- ambiguity error contract,
- full worked example with all candidates listed.
