============================================================
0. NORTH STAR
============================================================

L-01 introduced the ToolBlueprint contract.
L-02 introduced Observation.
L-03 introduced ExperimentRun lifecycle tracking.
L-04 introduced controlled experiment execution.
L-05A introduced the evaluation layer.

L-05B introduces temporal replay.

Core distinctions:

- Evaluation interprets observations at a given moment.
- Temporal Replay reconstructs what the SYSTEM KNEW at a given moment.
- Replay is NOT re-execution.
- Replay is NOT versioned content reconstruction (see NOTE 6, NOTE 12).
- Replay is read-only with respect to domain claims.
- Event time is NOT knowledge time (see NOTE 11).

Mission:
Implement the smallest complete temporal replay subsystem compatible
with the existing repository.

The subsystem must:
1. Accept an explicit replay request with an as_of cutoff.
2. Identify all domain entities KNOWN TO THE SYSTEM at that moment,
   using authoritative availability timestamps, not event times.
3. Reconstruct the set of Observations, ExperimentRuns, Predictions,
   Hypotheses, Phenomenon, and Evaluations available at that moment.
4. Derive historical statuses from status history where available.
5. Exclude any entity whose availability timestamp is after as_of.
6. Classify each reconstructed entity with historical fidelity
   (VERIFIED / PARTIAL / UNKNOWN).
7. Report reconstruction completeness (COMPLETE / PARTIAL / INCOMPLETE).
8. Preserve provenance and relations using existing mechanisms,
   filtered by their own timestamps.
9. Produce a structured replay result.
10. Never execute experiments, retry execution, or re-run evaluation.
11. Never rewrite past records.
12. Document versioning gaps explicitly.

Do not implement L-05C Integration Verification. That belongs to L-05C.

NOTE 6 — Versioning gap (CRITICAL)

The repository does NOT version the CONTENT of domain entities.
Prediction, Hypothesis, DiscoveryRecovery, Phenomenon, and
PotentialPhenomenon have only created_at and no version history.

This means temporal replay CAN reconstruct:
- WHICH entities existed at a given moment.
- WHICH observations were AVAILABLE (see NOTE 11).
- WHICH experiment runs existed.
- WHICH evaluations had been made.

But temporal replay CANNOT reconstruct:
- The historical CONTENT of a Prediction at a past moment.
- The historical CONTENT of a Hypothesis.
- The historical CONTENT of a Phenomenon.

The engine MUST document this limitation explicitly in the replay
result. The engine MUST NOT claim accurate historical content
reconstruction.

Do NOT introduce versioning in L-05B. Document the gap; a future
task may address it.

NOTE 7 — Provenance and Relations
Reuse ProvenanceRecord (smos/models/ecology.py) and
Relation / RelationType (smos/models/models.py).
Do not create parallel mechanisms.
Filter relations and provenance records by their OWN timestamps,
not just by whether they are currently linked to an old entity.

NOTE 8 — Uncertainty is preserved
Missing, invalid, or insufficient historical data must not be
silently converted into confident reconstruction.

NOTE 9 — Replay persistence modes

Replay operates in one of two modes:

Mode A — Computation-only (default):
    Compute the replay result and return it. Do NOT persist any
    replay record. No new database model is required.

Mode B — Persisted replay (conditional):
    Persist an append-only replay record. This mode is allowed
    ONLY when the audit proves that existing persistence
    mechanisms can store the replay record without modifying
    protected files or introducing a migration.
    If no compatible mechanism exists, Mode B MUST NOT be
    implemented.

Do not create a new database model automatically.
Do not create a migration.

NOTE 10 — Replay vs Sequence Replay (different mechanisms)

The repository has Sequence Replay and Batch Template Replay in
smos/core/sequences.py, smos/core/batch.py, and smos/api/main.py.
These are WORKFLOW replay mechanisms (replay of task sequences),
NOT temporal replay of research state.

Do NOT reuse or extend these mechanisms.
Create a distinct temporal replay subsystem.

NOTE 11 — Knowledge Time vs Event Time (CRITICAL)

Temporal replay reconstructs what was AVAILABLE TO THE SYSTEM,
not merely what had happened in the external world.

- observed_at represents event time.
- created_at represents record creation time.
- An authoritative ingestion/availability timestamp, if one
  exists, determines when a record became AVAILABLE to the system.

Event time MUST NOT substitute for knowledge time.

Example: an observation that occurred Monday but was ingested
Wednesday MUST NOT appear in a replay of Tuesday.

The audit MUST determine whether created_at accurately represents
system availability or whether ingestion can occur later.
If authoritative availability time cannot be established for a
record, mark its temporal eligibility as UNKNOWN and exclude it
from the VERIFIED reconstruction.

NOTE 12 — Historical State vs Current Entity Content (CRITICAL)

Entity existence and entity content are separate claims.

A created_at <= as_of condition proves neither that current
mutable content existed at as_of nor that current relations
existed then.

Every reconstructed entity MUST expose a historical fidelity
classification:

- VERIFIED: supported by authoritative historical records.
- PARTIAL: existence or some fields are supported, but historical
  content or relations are incomplete.
- UNKNOWN: insufficient evidence to establish the requested
  historical state.

Do not claim historical content reconstruction without
authoritative version history.

NOTE 13 — Status Reconstruction

For ExperimentRun and any other entity with status history,
derive the status at as_of from the latest authoritative status
transition available by that cutoff.

Never use a current status as a historical status without evidence.

If status history is absent, incomplete, or temporally ambiguous,
report UNKNOWN and explain why.

NOTE 14 — Consistent Read Snapshot

The engine MUST use an existing transaction or snapshot mechanism
when supported to prevent concurrent writes from producing an
internally inconsistent replay.

If the repository's persistence layer does not provide snapshot
isolation, document the limitation explicitly. Do not invent
guarantees.

NOTE 15 — Content Hash vs Execution Metadata

reconstructed_at naturally changes between runs. If included in
the hash of the entire result, identical reconstructions would
produce different hashes.

Solution:
- content_hash MUST be computed over the canonical historical
  result and the format version.
- reconstructed_at and run metadata MUST be stored separately.

The canonical serialization MUST specify:
- key ordering
- timezone rules
- collection ordering
- representation of missing values
- format version

The result MUST separately indicate whether source integrity was
verified. record_hash is NOT a proof of historical accuracy.

============================================================
2. DESIGN
============================================================

PART A — ReplayRequest

Fields:
- as_of (required): the cutoff moment.
- scope (optional): entity types to include.
- mode (optional): "computation" (default) or "persisted".
- Optional actor / reason metadata.

Validation:
- as_of must be a valid timezone-aware datetime.
- scope must be from an allowed set.
- mode "persisted" allowed only if infrastructure supports it.

PART B — ReplayResult

Fields:
- as_of (echo).
- format_version.
- reconstructed_state:
  - observations: [{id, availability_at, fidelity}]
  - experiment_runs: [{id, status_at_as_of, status_source,
                       availability_at, fidelity}]
  - evaluations: [{id, status, evaluated_at, availability_at,
                   fidelity}]
  - predictions: [{id, availability_at, fidelity}]
  - hypotheses: [{id, availability_at, fidelity}]
  - phenomenon: [{id, availability_at, fidelity}]
- reconstruction_diagnostics:
  - excluded_counts: per entity type, counts and reasons.
  - unknown_availability: per entity type, counts.
  - missing_status_history: per ExperimentRun, reasons.
  - versioning_gap: { entities: [...], impact: "content not
                     historically verifiable" }.
  - snapshot_isolation: { supported: bool, limitations: str }.
- provenance:
  - provenance_refs used.
  - relation_refs used, time-filtered.
- completeness: COMPLETE | PARTIAL | INCOMPLETE.
- uncertainty_notes.
- content_hash: over canonical historical result + format_version.
- reconstructed_at: separate from content_hash.
- source_integrity_verified: bool.

PART C — TemporalReplayEngine

Flow:
1. Validate the replay request.
2. Open a consistent read snapshot if supported (NOTE 14).
3. For each entity type, filter by AUTHORITATIVE AVAILABILITY
   timestamp (created_at or equivalent ingestion time), NOT event
   time (NOTE 11).
4. For ExperimentRun, derive status at as_of from status_history
   (NOTE 13).
5. Classify each entity's historical fidelity: VERIFIED, PARTIAL,
   or UNKNOWN (NOTE 12).
6. Filter provenance and relations by their own timestamps.
7. Compute reconstruction completeness (COMPLETE / PARTIAL /
   INCOMPLETE).
8. Populate diagnostics, including versioning_gap.
9. Compute content_hash over canonical historical result only
   (NOTE 15).
10. Persist a replay record only in Mode B, if supported.
11. Return the structured ReplayResult.

The engine MUST NOT:
- Execute an experiment.
- Re-run evaluation.
- Modify any existing record.
- Use observed_at as knowledge time.
- Include entities whose availability is after as_of in the
  reconstructed_state.
- Claim content reconstruction without versioning.
- Include reconstructed_at in the content_hash.
