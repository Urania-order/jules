============================================================
1. OBJECTIVE
============================================================

Define a typed ToolBlueprint contract that:

    - DESCRIBES a research tool (not executes it)
    - is versioned
    - links to research context
    - declares parameters, ranges, units
    - declares expected outputs
    - declares environment requirements as METADATA ONLY
    - preserves provenance
    - supports domain extensions via explicit namespaced
      `extensions` field
    - validates mandatory fields, types, ranges
    - rejects unknown core fields

============================================================
2. DESIGN
============================================================

PART A — Contract structure (minimum required)

    {
        "blueprint_id": str,               # stable identifier
        "version": str,                     # semver MAJOR.MINOR.PATCH
        "research_context": {
            "research_project_id": Optional[str],
            "phenomenon_id": Optional[int],
            "assumption_refs": List[str],
            "prediction_refs": List[int],
            "experiment_refs": List[str],
        },
        "specification": {
            "title": str,
            "description": str,
            "tool_type": str,               # core enum
            "parameters": List[ParameterSpec],
            "expected_outputs": List[OutputSpec],
        },
        "environment": {
            "runtime_requirements": Dict,   # declarative METADATA only
            "security_policy": Dict,        # declarative METADATA only
        },
        "provenance": {
            "created_by": str,
            "created_at": str,              # ISO8601
            "parent_version": Optional[str],
            "provenance_metadata": Dict,    # metadata only
        },
        "extensions": {                     # NEW: namespaced domain extensions
            "<namespace>": Dict,            # e.g. "recipe", "lab", "multi-agent"
        },
    }

CRITICAL — separate concerns:
    - provenance — origin, authorship, timestamps, parent-version refs
    - extensions — domain-specific additions, namespaced
    - Never mix; do NOT put domain extensions inside provenance_metadata.

PART B — ParameterSpec

    {
        "name": str,
        "type": str,               # "float" | "int" | "string" | "bool" | "enum"
        "unit": Optional[str],
        "min": Optional[float],    # numeric types only
        "max": Optional[float],    # numeric types only
        "default": Optional[Any],  # must match declared type
        "allowed_values": Optional[List],   # enum type only
        "required": bool,
        "description": Optional[str],
    }

PART C — OutputSpec

    {
        "name": str,
        "type": str,               # "float" | "int" | "string" | "bool"
                                   # | "timeseries" | "json"
        "unit": Optional[str],
        "description": Optional[str],
    }

PART D — Core tool_type enum

    Known values:
        DATA_COLLECTION
        SIMULATION
        VISUALIZATION
        OBSERVATION_FORM
        ANALYSIS_INTERFACE
        EXPERIMENT_PLANNER

    Unknown tool types MUST be rejected unless they are
    accepted by an explicit, documented extension-registration
    mechanism.

    TASK L-01 does NOT implement a full plugin system.
    TASK L-01 does NOT assume an extension registry exists.
    If repository audit does NOT already have a suitable
    registry, reject unknown tool types.

PART E — STRICT type and range validation

    Type validation:
        - int parameter MUST reject fractional values (2.5)
        - bool MUST NOT pass as int or float
        - int MUST NOT pass as bool (Python bool is int subclass)
        - float MUST NOT accept NaN or infinity
        - string MUST be str, not bytes

    Range validation:
        - numeric bounds (min, max) applied ONLY to int and float
        - if min and max present: min < max
        - if default present: min <= default <= max
        - if type == "enum": allowed_values required, non-empty,
          and default (if present) MUST be in allowed_values
        - if type != "enum": allowed_values MUST be absent

    required / default interaction:
        - `required` refers to whether a VALUE must be supplied
          by the caller at execution time
        - `required` does NOT mean the value must be known at
          Blueprint creation time
        - a required parameter MAY have a default

    Reject:
        - unknown core fields
        - unknown tool_type (unless explicitly registered)
        - contradictory parameter definitions
        - invalid default type
        - non-finite numeric values
        - empty enum allowed_values

PART F — STRICT input structure

    from_dict() MUST reject unknown core fields rather than
    silently ignoring them.

    Blueprint payloads MUST NOT accept:
        - epistemic_status
        - evidence
        - actual_outcome
        - any other conclusion/result-bearing field

    Domain-specific additions MUST pass ONLY through the
    explicitly validated `extensions` field.

    Blueprint validation MUST NOT mutate canonical domain
    entities or prediction state.

PART G — Serialization & versioning

    Canonical serialization MUST be defined BEFORE implementing
    version_hash().

    Canonical form:
        - sorted keys
        - deterministic value formatting
        - explicit serialization of lists and dicts
        - INCLUDE version in the hashed payload

    version_hash():
        - SHA-256 over canonical serialization of the entire
          immutable Blueprint, INCLUDING version
        - stable across equivalent canonical data
        - changes when meaningful Blueprint content or version
          changes
        - MUST NOT be presented as a guarantee of reproducible
          execution (no execution exists at this stage)

    diff(other):
        - deterministic structured description of changed fields
        - returns empty diff for identical canonical Blueprint
        - returns structured diff for differing fields

PART H — Epistemic guarantees

    Blueprint MUST NOT have:
        - epistemic_status field
        - evidence field
        - actual_outcome field
        - any field implying validation of hypotheses

    Blueprint MAY reference:
        - prediction_ids (before outcomes)
        - assumption identifiers (as opaque strings)

    Blueprint MUST NOT:
        - copy prediction.actual_outcome
        - promote any hypothesis
        - auto-execute

PART I — Extension mechanism

    Domain extensions live ONLY under `extensions`:
        extensions: {
            "recipe": {...},
            "lab": {...},
            "multi_agent": {...},
        }

    Core validation rules MUST NOT be bypassed by extension
    fields.

    TASK L-01 does NOT implement a full plugin system.

    Extensions are validated against:
        - namespace is a string
        - payload is a dict
        - payload does NOT contain core-reserved keys
          (epistemic_status, evidence, actual_outcome)

PART J — Authoritative validation location

    Validation logic MUST live in ONE authoritative location.

    Do NOT duplicate rules between the contract and the
    service.

    If existing repository pattern puts contract validation in
    the model file (like TASK 22/24), follow that pattern.
    Otherwise, choose one location and document it.
