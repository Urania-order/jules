0. NORTH STAR
============================================================

L-01 introduced the ToolBlueprint contract.
L-02 introduced Observation.
L-03 introduced ExperimentRun lifecycle tracking.
L-04 introduced controlled experiment execution.

L-05A introduces the evaluation layer.

The core distinction is:

- Execution produces an outcome.
- Observation records a measurement.
- Evaluation interprets observations against an explicit target
  and evaluation criteria.
- Evaluation does not automatically establish truth.
- Evaluation does not automatically change epistemic status.
- Evaluation must preserve uncertainty, provenance, and the basis
  of its conclusion.

Mission:
Implement the smallest complete evaluation subsystem compatible
with the existing repository.

The subsystem must:
1. Accept an explicit evaluation request.
2. Identify the target Prediction, Hypothesis, or other supported
   research entity using existing domain conventions.
3. Retrieve only observations and contextual data eligible for
   the evaluation.
4. Apply explicit, inspectable evaluation criteria.
5. Distinguish confirmed, refuted, inconclusive, and undetermined
   outcomes where those states are semantically justified.
6. Preserve provenance, timestamps, criteria, and uncertainty.
7. Produce a structured evaluation result.
8. Persist evaluation history if existing infrastructure cannot
   provide equivalent durable records.
9. Permit later inspection and temporal reconstruction of the
   evaluation.
10. Never automatically promote, demote, or otherwise mutate
    epistemic status.

Do not implement Temporal Replay itself. That belongs to L-05B.

2. DESIGN
============================================================

PART A — EvaluationStatus
Define or reuse an appropriate status representation.
Candidate statuses:
- CONFIRMED
- REFUTED
- INCONCLUSIVE
- UNDETERMINED

Semantic requirements:

CONFIRMED
The observed result satisfies the explicit evaluation criteria
for the specified target and evaluation scope.
This status describes the result of the evaluation, not universal
or permanent truth.

REFUTED
The observed result contradicts the explicit evaluation criteria
for the specified target and scope.
Absence of an expected observation is not sufficient by itself to
establish refutation.

INCONCLUSIVE
Evaluation was performed, but the available valid observations do
not distinguish adequately between competing interpretations or
outcomes.

UNDETERMINED
A defensible evaluation cannot be established because required
inputs, applicable criteria, or necessary temporal/provenance
information are missing or invalid.

Use existing repository terminology when a compatible status
already exists.
Do not use a status to conceal an operational error. Validation
errors and failed evaluation attempts must remain inspectable
through the repository's existing error conventions.
Do not introduce additional statuses without a demonstrated need.

PART B — EvaluationRecord
First search for an existing persistent record capable of
representing the required information.
If a new record is justified, its minimum conceptual information
should include:
- Stable record identifier.
- Target entity type and identifier.
- Associated Prediction identifier, where applicable.
- Evaluation status.
- Evaluation timestamp.
- Temporal cutoff, if requested and supported.
- References to the observations used.
- Criteria identifier, version, or canonical representation.
- Structured rationale or criterion-level findings.
- Uncertainty or limitations.
- Provenance.
- Evaluation implementation/version information where needed for
  reproducibility.
Use actual repository field and relationship conventions.
Do not store duplicate copies of large domain entities when stable
references suffice.
Do not make the record imply that the target entity's epistemic
status has changed.

Record immutability:
Prefer append-only evaluation history.
A new evaluation must not silently overwrite a prior result. If
the repository supports corrections or revisions, use its
established mechanism and preserve access to the previous record.
Do not invent a second versioning system if a canonical one
already exists.

PART C — Evaluation contract
Define a request contract and result contract using existing
validation conventions.
The exact fields must be grounded in the repository audit.

Conceptual request fields:
- Target entity type and identifier.
- Optional Prediction identifier.
- Explicit evaluation criteria or reference to a registered
  criterion set.
- Optional as_of cutoff.
- Optional actor/request metadata, if compatible with existing
  conventions.
The caller must not be allowed to replace authoritative target data
or fabricate observations by supplying arbitrary IDs and values.
The engine must validate that referenced entities exist and that
the requested target relationships are valid.
Do not accept executable code, arbitrary expressions, or
unvalidated scoring instructions as criteria.

Result contract:
The structured result should expose, as supported by the
architecture:
- Evaluation identifier, if persisted.
- Target reference.
- Evaluation status.
- Criteria used.
- Observations considered and excluded.
- Criterion-level findings.
- Rationale.
- Uncertainty and limitations.
- Evaluation timestamp and temporal cutoff.
- Provenance.
- Structured operational errors, where applicable.
Use deterministic serialization if the result is hashed or
compared for reproducibility.
Validation must not mutate caller-owned inputs.
Do not add automatic epistemic promotion fields or side effects.

PART D — EvaluationEngine
Create or extend the canonical service responsible for explicit
evaluation.

Conceptual flow:
1. Validate the evaluation request.
2. Load the authoritative target and related Prediction.
3. Resolve the applicable criteria.
4. Select eligible observations and supporting context.
5. Enforce the temporal cutoff when requested.
6. Validate observations and required provenance.
7. Apply explicit evaluation logic.
8. Determine the result status without inventing certainty.
9. Record rationale, uncertainty, exclusions, and provenance.
10. Persist the evaluation record if required by the audited
    architecture.
11. Return a structured result.

The actual method names and signatures must follow repository
conventions.

The evaluation service must not:
- Execute an experiment.
- Create fabricated observations.
- Automatically generate missing data.
- Change epistemic status.
- Rewrite a hypothesis or prediction.
- Automatically promote a conclusion.
- Run a temporal replay.
- Claim historical reproducibility when the underlying data
  versions are unavailable.

Evaluation criteria:
Criteria must be explicit and inspectable.
Reuse existing domain criteria if present.
If no evaluation algorithm exists for a target type, do not invent
a scientifically meaningful algorithm merely to make the test
pass. Either implement a narrow, clearly documented deterministic
rule supported by the existing contract or return an appropriate
inconclusive/undetermined result.
Distinguish operational success from evaluation validity.

relevant exclusions and temporal boundaries, to the extent
supported by the actual schema.

append-only records or the existing revision mechanism.

Invariant 6 — Evaluation is explicit and read-only with respect to
domain claims
Evaluation occurs only when explicitly requested. It may create an
evaluation record, but must not execute tools or mutate the
epistemic state of the evaluated entities.
