GOAL:
Add a backend endpoint that the frontend batch button can call.

REQUIREMENTS:

1. POST /api/batch/run
Request body:
  {
    "task_ids": ["task-...", ...],
    "schedule": "now" | "now-sequential" | "night" | "window",
    "concurrency": 1..10
  }

Semantics:
- "now": run up to N tasks in parallel (respect concurrency).
- "now-sequential": run one at a time.
- "night": queue for off-hours (store, do not execute immediately).
- "window": use existing schedule if present; else return 400
  with code SCHEDULER_NOT_IMPLEMENTED.

Response:
  {
    "status": "accepted" | "queued" | "error",
    "batch_id": "batch-...",
    "task_ids": [...],
    "concurrency": N,
    "schedule": "...",
    "started": [list of task_ids started],
    "queued": [list of task_ids queued]
  }

2. GET /api/batch/{id}
Return batch status.

3. GET /api/batch
List recent batches.

4. GET /api/batch/queue
List currently queued batches.

CONSTRAINTS:
- Reuse existing task dispatch logic (do not duplicate).
- Reuse existing autonomy logic (MANUAL/ASSISTED/AUTO) from Patch B.
- Do NOT execute tasks under MANUAL without explicit confirm=true.
- Respect concurrency limit.
- "night" and "window" MUST NOT start tasks immediately.
- Return 400 with SCHEDULER_NOT_IMPLEMENTED if "window" is requested
  and no scheduler backend exists.
- Do not invent a scheduler backend in this task.
  Just store the batch and return "queued".
- Do not touch .co-smos/, .jules/tasks/, .jules/results/, .jules/queue/.
