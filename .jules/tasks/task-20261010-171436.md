DEFINITIONS — FOUR CLASSES
============================================================

For each property, STEP 0 MUST classify into ONE of:

(1) GUARANTEED
    Current code guarantees the property.

(2) PARTIAL
    Current code guarantees the property only under
    specific conditions.

(3) DEFECT
    Current code VIOLATES the desired property.
    → STOP (see WHAT HAPPENS ON STOP).

(4) ARCHITECTURAL GAP
    The property is not supported by current
    architecture (e.g. historical replay, input
    snapshots per ADR-0009).
    → Record the gap with reference to ADR-0009.
    → Do NOT write a test that simulates support.

============================================================

============================================================

allowed ONLY when:

    the ACTUAL behavior does NOT violate any of the
    properties AND is a valid existing contract of
    Co-SMOS.

    → DEFECT.
    → Do NOT write a passing test that documents the
      defect as "acceptable behavior".
    → STOP without commit.
    → Report the defect in the FINAL REPORT.

Property 1 — Same H₀, different contexts:
    Two contexts with CONCRETE semantic differences
    (different DomainRelation links, OR constraints,
    OR potentials) — NOT merely different names.
    Assert analysis reflects those differences.
    If code does NOT guarantee context-dependent results:
        → DEFECT.

Property 2 — Blockage ≠ impossibility:
    Blocked potential remains a possibility, just blocked.
    If code treats blockage as impossibility:
        → DEFECT.

Property 3 — Absence of data ≠ evidence of absence:
    Missing data MUST NOT become a false claim.
    If code claims "does not exist" from no data:
        → DEFECT.
    If code records "unknown" / "unresolved":
        → assert ACTUAL behavior.

Property 4 — Competing hypotheses:
    Two Phenomenon entities MAY coexist.
    BUT coexistence alone does NOT prove that an
    alternative/competition mechanism exists.

    The classification MUST separate:
        (4a) entity coexistence — may be GUARANTEED
        (4b) alternative/competition handling —
             may be ARCHITECTURAL GAP

    Do NOT classify the entire property as GUARANTEED
    merely because coexistence is possible.

    If no explicit alternative/competition mechanism
    exists:
        → record unsupported alternative handling as
          ARCHITECTURAL GAP.

Property 5a — Current-state rerun reflects current state:
    STEP 0 MUST determine whether current-state rerun
    behavior is guaranteed.
    If guaranteed or partial:
        → write a test for the VERIFIED contract.
    If violated:
        → DEFECT.
    If architecture does not support:
        → ARCHITECTURAL GAP.

Property 5b — Historical result immutability (if supported):
    If STEP 0 confirms stored historical result exists:
        → assert stored result unchanged.
    If STEP 0 confirms NO stored historical result:
        → ARCHITECTURAL GAP (per ADR-0009).
        → Do NOT write a passing test.

Property 5c — Input snapshot availability (if supported):
    If STEP 0 confirms input snapshot mechanism exists:
        → assert snapshot retrieval.
    If STEP 0 confirms NO input snapshot mechanism:
        → ARCHITECTURAL GAP (per ADR-0009).
        → Do NOT write a passing test.

Property 6 — Explainability of differences:
    If STEP 0 confirms no input snapshot mechanism:
        → ARCHITECTURAL GAP (reference ADR-0009).
        → Do NOT write a passing test claiming
          explainability.
    If some mechanism exists (e.g. DomainEvent log):
        → assert ACTUAL behavior of that mechanism.
