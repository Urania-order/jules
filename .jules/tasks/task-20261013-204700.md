============================================================
0. NORTH STAR
============================================================

L-01 introduced the ToolBlueprint contract.
L-02 introduced Observation and its contract.
L-03 introduced ExperimentRun lifecycle tracking.
L-04 introduces a controlled execution engine connecting these components.

The engine must execute only explicitly registered, permitted operations.
It must not interpret a ToolBlueprint specification as executable code.

The engine must preserve the distinction between:
- a proposed experiment;
- an approved experiment;
- an execution attempt;
- a completed execution;
- observations produced by that execution;
- subsequent epistemic evaluation.

Execution is not evaluation. An observation is not a fact.
A completed run does not confirm a hypothesis.

Mission:
Implement an explicit execution engine that:
1. Accepts an existing ExperimentRun.
2. Verifies that the run is eligible for execution.
3. Resolves its ToolBlueprint reference through an explicit, allowlisted
   executor registry.
4. Validates and passes parameters to the registered executor.
5. Captures the execution outcome, timing, and provenance.
6. Converts successfully returned measurements into Observation records
   using the existing L-02 contract and service.
7. Returns a structured execution result.
8. Preserves the existing lifecycle rules and never evaluates or promotes
   epistemic claims.

No execution may occur without an explicit caller request.

NOTE 8 — Failure-path contract (CRITICAL)

After ExperimentRunService.execute() succeeds (APPROVED -> EXECUTED),
the run is in EXECUTED state. The following outcomes are possible:

A. Executor raises exception or returns malformed output:
   -> Engine MUST call ExperimentRunService.fail(run_id, reason)
   -> EXECUTED -> FAILED
   -> Do NOT ingest observations
   -> Do NOT call complete()
   -> Do NOT report success
   -> Do NOT retry automatically

B. Executor succeeds, but observation ingestion fails partway:
   -> Some observations may already be persisted (external side effect
      OR partial DB write).
   -> Engine MUST NOT claim full success.
   -> Engine MUST report partial persistence explicitly in the result.
   -> Engine MUST NOT automatically retry the operation, because:
        - the external side effect may already have occurred,
        - retrying would risk duplicate side effects.
   -> Document the limitation: exactly-once semantics require durable
      coordination, which is not available in L-04.
   -> The caller is responsible for deciding whether to fail() the run
      or to accept the partial result.

C. Executor succeeds, all observations ingested:
   -> Engine MUST call ExperimentRunService.complete(run_id,
      observation_refs=ingested_ids)
   -> EXECUTED -> COMPLETED
   -> Report success with observation IDs.

D. Executor returns no measurements (empty success):
   -> Engine MUST call ExperimentRunService.complete(run_id,
      observation_refs=[])
   -> EXECUTED -> COMPLETED
   -> Report success with empty observation list.

CRITICAL BOUNDARY:
The engine must never silently retry after a real external effect.
If retry safety cannot be guaranteed, the engine must fail loudly
and defer the decision to the caller.

2. ARCHITECTURE
============================================================

PART A — Explicit executor interface
Define a minimal executor protocol compatible with the repository's
existing conventions.
Conceptual interface:
    execute(parameters, execution_context) -> structured_result
The exact signature must follow the repository audit.
Every executor must:
    - Be explicitly registered.
    - Have a stable executor identifier.
    - Validate its input parameters.
    - Return a structured result.
    - Report errors without fabricating successful output.
    - Respect the execution context and supported resource limits.
The engine must resolve executors through an explicit allowlist.
Unknown executor identifiers must be rejected.
Do not dynamically import arbitrary modules, evaluate strings, or
execute code supplied in a ToolBlueprint.

PART B — Executor registry
Provide an explicit registry, or reuse an existing registry if compatible.
Required behavior:
    - Register an approved executor.
    - Resolve a registered executor.
    - Reject unknown identifiers.
    - Reject duplicate registrations unless the existing architecture
      explicitly supports safe replacement.
    - Provide a deterministic way to inspect registered executor identifiers.
Registration must not execute an operation.
No automatic discovery of arbitrary Python modules.

PART C — Execution contract
Define a contract for execution inputs and results.
The precise schema must follow the existing ToolBlueprint contract.
At minimum, validate the following conceptual fields.

Execution request:
    - experiment_run_id
    - parameters
    - Optional caller/actor identifier
    - Optional request idempotency key, if compatible with existing conventions
The engine must obtain the authoritative blueprint reference and run
status from the persisted ExperimentRun, not trust caller-supplied
replacements.

Execution result:
    - experiment_run_id
    - executor_id
    - status: SUCCEEDED or FAILED
    - started_at
    - finished_at
    - Structured output or validated measurements
    - Structured error information, if failed
    - Provenance
    - A stable execution-attempt identifier if supported by the persistence design
Use deterministic canonical serialization for structured payloads when
hashing is needed.
Do not add epistemic_status, evidence, or hypothesis-promotion fields to
execution results.
Do not confuse executor success with scientific validity.

PART D — Run eligibility
The engine must load the persisted ExperimentRun and check its actual
lifecycle state.
Only a run explicitly approved for execution may enter the execution path.
The execution engine must reject:
    - Missing runs.
    - Proposed runs.
    - Cancelled runs.
    - Completed runs.
    - Failed runs.
    - Runs with malformed parameters.
    - Runs referencing an unknown or unregistered executor.
    - Runs whose blueprint contract fails validation.
The exact transition behavior must be compatible with L-03.
If L-03 requires an explicit execute() service call to transition
APPROVED to EXECUTED, reuse that transition. Do not silently redefine
its semantics.
Do not execute an operation as a side effect of propose() or approve().
Do not automatically retry a failed operation.

PART E — Execution outcomes
The engine must distinguish:
    1. Successful execution with valid output.
    2. Successful execution with no measurements.
    3. Executor failure.
    4. Invalid executor output.
    5. Unknown executor.
    6. Invalid input.
    7. Ineligible lifecycle state.
    8. Timeout or resource-limit failure, if supported by the actual
       execution environment.
Errors must be explicit and inspectable.
A failed execution must not generate fabricated Observation records.
If an executor returns malformed output, reject the malformed output and
record or return the failure using existing persistence conventions.
Do not convert an invalid output into a successful empty result.

5. LIFECYCLE INVARIANTS
============================================================

All existing L-03 invariants remain in force.

Invariant 1 — Explicit execution
    An execution occurs only after an explicit execution request.
    Approval alone never executes a tool.

Invariant 2 — No automatic lifecycle transitions
    Do not automatically approve a run.
    Do not automatically start another run.
    Do not automatically retry failures.
    Do not automatically evaluate results.

Invariant 3 — No epistemic promotion
    Observations remain observations.
    Predictions and hypotheses are not modified by the execution engine.
    Do not change epistemic statuses or conclusions.

Invariant 4 — Auditable outcomes
    Each execution attempt must return a structured outcome.
    If durable execution-attempt history is required but unsupported by the
    existing schema, report the gap rather than pretending that transient
    logs provide durable history.

Invariant 5 — No silent success
    If execution, output validation, or required observation persistence fails,
    the engine must not report complete success.

Invariant 6 — Existing lifecycle remains authoritative
    ExperimentRunService remains the canonical owner of lifecycle transitions.
    The execution engine must not create a second independent state machine.
