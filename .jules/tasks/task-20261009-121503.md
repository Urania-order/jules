0. NORTH STAR
============================================================

TASK 28 established the derived semantic retrieval foundation.
TASK 29-34 integrated semantic retrieval into existing analytical
services without promoting similarity to evidence.
TASK 35 exposes existing semantic retrieval through read-only API
endpoints.

TASK 36 adds a minimal Semantic Exploration UI over the existing API.

The operator must be able to:
- submit a semantic search query;
- optionally filter by entity types;
- choose a result count;
- inspect semantic candidates;
- request similar candidates for any displayed result;
- explore Similar -> Similar repeatedly;
- return to the original search results without repeating the search;
- understand empty, loading, validation, authentication, and error states.

CRITICAL PRINCIPLE:

SEMANTIC SIMILARITY IS A CANDIDATE-GENERATION SIGNAL.
IT IS NOT EVIDENCE, CAUSATION, RESONANCE, OR EPISTEMIC TRUTH.

Navigation is deliberately SINGLE-LEVEL.
Deep exploration is allowed, but navigation history is not a stack.

============================================================
2. OBJECTIVE
============================================================

Add a minimal Semantic Exploration screen using the existing TASK 35 API.

The UI has two logical views:

A. SEARCH VIEW
- query input;
- optional comma-separated entity-type filter;
- result-count control, default 10;
- search action;
- ordered result list;
- Find similar action on every result.

B. SIMILAR VIEW
- identifies the selected source entity;
- displays the API's similar candidates;
- provides a Back action to return to the retained Search View;
- provides Find similar on every candidate;
- replaces the current Similar View when exploring another candidate.

The UI must use the existing frontend architecture.

Do not add a framework, component library, backend service, or API
endpoint for this feature.

============================================================
3. USER INTERACTION CONTRACT
============================================================

3.1 Search query

Provide:
- text input;
- search button;
- result-count control;
- optional entity-type filter.

Default k = 10.
Allowed k = 1 through 100.

Validate the query before submitting:
- empty or whitespace-only input must not be submitted;
- show a concise validation message;
- do not silently transform the user's query beyond trimming for
  the empty-input check.

Send the query using the actual TASK 35 request contract.

The backend remains authoritative for validation.

3.2 Entity-type filter

The filter is optional.

If the existing frontend already has an appropriate filter convention,
reuse it if it satisfies the contract below.

Otherwise, the minimum viable UI is a text input accepting
comma-separated entity types.

Parsing rules:
- empty input -> entity_types: null;
- whitespace-only input -> entity_types: null;
- "phenomenon, constraint" -> ["phenomenon", "constraint"];
- "phenomenon,,constraint" -> ["phenomenon", "constraint"];
- trim surrounding whitespace;
- drop empty entries.

Example:
    "phenomenon, constraint"
becomes:
    ["phenomenon", "constraint"]

Use actual identifiers discovered during STEP 0.

Do not invent a canonical entity-type list.

Apply the selected filter to requests according to the actual TASK 35
contract. Do not silently change filter semantics between views.

3.3 Search execution

On submission:
- call POST /api/semantic/search;
- send query, k, and entity_types;
- display the returned candidates in API order;
- preserve entity_type and entity_id exactly as returned.

Do not:
- sort results again;
- recalculate similarity;
- add a threshold;
- add a confidence classification;
- group or cluster results;
- hide candidates because their scores appear low.

3.4 Result presentation

Each result displays, when supplied:
- entity_type;
- entity_id;
- similarity;
- model_name.

Use clear field labels.

Similarity is a numeric retrieval signal only.

Do not call it:
- probability;
- confidence;
- truth;
- causal strength;
- evidence;
- resonance;
- epistemic status.

Do not use colors, badges, or visual ranking to imply truth,
causation, or epistemic correctness.

Do not infer entity descriptions from identifiers.

3.5 Find similar — REPLACEABLE SIMILAR VIEW

Every result in the Search View has a Find similar action.

When activated:
- call GET /api/semantic/similar/{entity_type}/{entity_id};
- pass the selected k;
- pass entity-type filters according to the verified TASK 35 contract;
- display the actual returned candidates in the Similar View.

Path parameters must be encoded safely using the existing URL-building
conventions. Do not build unsafe URLs from untrusted values.

Every candidate displayed in the Similar View ALSO has a Find similar
action.

When activated:
- use that candidate's actual entity_type and entity_id;
- request its similar candidates;
- replace the current Similar View with the new results.

Similar -> Similar exploration may continue repeatedly.

This does NOT create a navigation stack.

The UI must not assume that the source entity is excluded from results.
Render the actual API response without adding client-side self-exclusion.

3.6 Navigation and retained state — SINGLE-LEVEL BACK

Navigation model: SINGLE-LEVEL BACK.

From Search View:
    Find similar
        -> Similar View for selected entity

From Similar View:
    Back
        -> Search View with its previous state restored

From Similar View:
    Find similar on a candidate
        -> replace current Similar View with that candidate's
           Similar View

Rules:
- Do not create a multi-level navigation stack.
- Do not add browser-history integration solely for this feature.
- Do not implement breadcrumbs representing an exploration chain.
- Do not imply that Back returns to the previous Similar View.
- Back always returns to the retained Search View.

Retain the Search View's:
- query;
- entity-type filter;
- result count;
- result list.

Returning to Search View must not repeat the search request.

The current Similar View may be replaced as many times as needed.

Use the smallest state mechanism compatible with the existing frontend.

Do not add persistent browser storage unless the existing application
already requires and safely supports it.

Do not create a global state framework for this feature.

3.7 Result count and filter during exploration

Use the current selected k when requesting similar candidates.

Use the current selected entity-type filter according to the actual
TASK 35 API contract.

The retained Search View must preserve its own query, filter, k,
and results even while Similar View requests are made.

Do not overwrite the retained Search View with Similar View state.

4. LOADING, EMPTY, ERROR, AND STALE REQUESTS
============================================================

4.1 Idle

Before the first search, show a clear initial state.

Do not imply that a search has already been performed.

4.2 Loading

Show a visible loading state while a request is active.

Prevent accidental duplicate submissions using the existing UI pattern.

Keep the interface responsive.

4.3 Results

Render the actual API response in the order received.

4.4 Empty results

Show a clear message that no candidates were returned.

Do not claim that the entity has no relationships or that the phenomenon
does not exist.

4.5 Validation error

Show a concise explanation for invalid input.

Do not submit the invalid request.

4.6 Authentication / authorization error

Use the actual API response and existing frontend authentication flow.

Show an appropriate access error.

Do not convert authorization failure into an empty result list.
Do not attempt to bypass authentication.

4.7 Network or server error

Show a concise error that does not expose internal server details.

Allow the operator to retry.

Do not silently convert a failed request into an empty result list.

Do not swallow non-abort errors.

4.8 Stale requests

An older response must never overwrite newer UI state.

Apply this to both Search and Similar requests.

STEP 0 must identify any existing request-cancellation or request-
identity pattern and reuse it if suitable.

If no suitable pattern exists and AbortController is supported,
use native AbortController without adding dependencies.

Required behavior:
- keep track of the active request controller;
- abort the previous applicable request when a newer request supersedes it;
- create a new controller for the new request;
- pass its signal to fetch or the existing compatible request wrapper;
- ignore AbortError as an expected cancellation;
- prevent a response from updating state if it is no longer current;
- continue displaying non-abort errors;
- ensure an old request cannot clear the loading state of a newer request.

Use a request identity/token check in addition to cancellation when
needed to guarantee that stale responses cannot update the UI.

If AbortController is unsupported, use a compatible request identity
mechanism and document the decision.

Cancellation is client-side control. Do not claim it guarantees that
server-side processing has stopped.

Do not add a dependency solely for stale-request handling.
